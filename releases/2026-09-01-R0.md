## Scope

R0 establishes the foundation for Phenotype Fabric. It does **not** include:

- Cross-machine route planning (PF-WP-020)
- I/O surface planes (PF-WP-030)
- Wire protocol over real network (PF-WP-040)
- Real-time audio/video transport (PF-WP-050+)

R0 is the **measurement** phase: discover capabilities, sign them, and
publish them. The next phase (R1) uses this foundation to make placement
decisions.

## Architectural decisions ratified

- **Cap-IDs are UUIDv7** (sortable + globally unique without coordination). `program/identifiers.md` is the source of truth.
- **Topology hash is BLAKE3** of the subgraph (compute + accelerator + display + pcie + topology). Audio/input/storage/network excluded because they don't affect placement.
- **Signatures are Ed25519** with base64 key fingerprints as `key_id`. The canonical bytes for signing **strip the `signatures` field** to prevent a signature from signing itself.
- **R0 stability is enough, not maximal** — using `serde_json::Value` round-trip for canonical bytes. Formal deterministic JSON (RFC 8785) is R1 work.
- **Cross-language adapter is Go, not C** — Go adapter is the contract surface for non-Rust consumers. C FFI is provided as a convenience for systems that need it.

---

## What's intentionally **not** in R0

- **Route planning** (PF-WP-020) — needs a way to model "what does the user want to do" beyond a single-machine capability. R1 work.
- **I/O surface planes** (PF-WP-030) — audio/video/window/device surfaces are large and need a separate WP. R2 work.
- **Wire transport** (PF-WP-040) — what's the protocol for exchanging descriptors between nodes? Sibling of route planning. R1 work.
- **Authoritative timing** — R0 is read-mostly; RT islands are a R2 concern.
- **Atomic placement** — R0 measures, R1 plans, R2 enforces.

## Risks identified (carried into R1)

| Risk | Severity | R1 mitigation |
|:--|:--|:--|
| Canonical-bytes stability | medium | Move to RFC 8785 (deterministic JSON) before R1.5 |
| Probe coverage on macOS is partial | low | Add IORegistry probe in R1 |
| No link-metrics probe (RTT, bandwidth) | medium | Add latency probe in R1 (PF-WP-020 dependency) |
| Ed25519 key rotation not specified | low | Add key-rotation policy in R1 |
| No replay protection on signed descriptors | medium | Add epoch + nonce validation in R1 |

## Open questions for the next session

1. **Is the `signatures` field canonicalization the right approach?** Alternative: include the signature in the canonical bytes and accept that signatures can only be added once (no re-signing without mutating). The current approach trades re-signability for a slightly weird canonicalization. See ADR-0014.
2. **Should the topology hash include `probed_at`?** Currently excluded; the same physical machine should produce the same hash even if probed at different times. But that means a changed GPU driver won't bump the hash. See ADR-0015.
3. **What does "RT-safe" mean for the probe itself?** Probes are run on a normal thread. Some measurements (e.g., interrupt-rate, scheduling latency) need RT context. Out of scope for R0 but needs a design doc in R1.
4. **Federation:** can a node trust a descriptor from a peer it hasn't met? Current R0 model is direct key trust only. R1 needs either a trust-root system or signed-by-CA model.
